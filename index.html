QA case study: testing a mobile banking channel

By Sharleen Njihia. I tested a small demo banking app and a public API, logged what broke, retested the fixes and wrote a release sign-off.

The short version

What: a demo mobile banking app with 7 deliberate defects, in two versions (v1.0 broken, v1.1 fixed).

What I did: wrote test cases, ran them on v1.0, logged each defect, retested on v1.1, checked the API calls behind Send money and wrote a sign-off.

Where to look: test cases and defects below, integration for the backend checks, test plan for scope.

Regression and API results

Regression scope for v1.1: all 9 test cases, because the fixes touched balance, transfer and history logic, which every journey depends on.

API suite: 5 checks on the API page: status codes, required fields, a not-found case and a create (POST) case.

Release sign-off: v1.1

OK to release v1.1.

All 7 defects (4 in the app, 3 in the backend calls) were fixed and retested. All 9 test cases pass. Nothing high or critical is still open. The backend results are on the integration page.

Not covered: performance, security and real phone networks. This is a demo with no real backend.

What I would improve next

  • 4 of the 7 defects ended with the wrong balance. Every test that moves money should also check the balance afterwards.
  • 2 defects gave the customer a poor message (DEF-03, DEF-07). Add a check on error wording to the test checklist.
  • Not tested yet: session timeout, tapping Send twice, and slow networks.
  • The regression tests repeat every release, so they are a good fit for automation later (for example Playwright).
