Test plan: Mock Mobile Bank v1.0 and v1.1

A test plan says what we will test, how, and when we can stop. This one is short on purpose.

QA dashboardTest planApp v1.0App v1.1IntegrationAPI tests

Objective

Check that the customer journeys in the mock mobile banking app work correctly, that errors are handled clearly, and that the app is safe to release. Check that data returned by an API matches what is expected.

Scope

In scopeOut of scope
Login with correct and wrong PINPerformance and load testing
Send money, including invalid amountsSecurity and penetration testing
Buy airtime and balance updateAutomated test scripts
Transaction historyReal backend, real money, real mobile networks
Layout on phone, tablet and laptop browsersUSSD channel (not built in this project)
5 API checks, plus integration of Send money with a backend service, including failure casesAccessibility audit

Approach

  • Functional testing: manual tests for normal use, error cases and navigation.
  • Compatibility testing: the same journeys on different devices, operating systems and browsers.
  • API testing: requests sent to a practice API, checking status code, response fields and values.
  • Defect retest: every fixed defect is checked again on v1.1.
  • Regression testing: all test cases re-run on v1.1, because the fixes touched balance and transfer logic that every journey uses.

Defect handling

Each defect is logged with an ID, title, steps to reproduce, actual and expected result, severity and priority. Severity is the impact on the customer or the bank. Priority is how soon it must be fixed. Defects move from Open to Fixed to Closed once retested.
